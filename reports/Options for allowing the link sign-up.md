# Let the backend create the password login, do not open the sign-up

There are **five workable ways** to resolve issue #41: an Action refuses a password sign-up when the email already belongs to a Vocab User, but a Google-only User must still be able to add a password. Four other ways are ruled out because they do not work or break a constraint. The recommendation is **option 4: the backend creates the password login through the Management API for the signed-in User, and the User sets the password through a reset email**. With this option the public sign-up form needs no exception. The Action keeps one refusal rule for everyone, and the reset email proves the User owns the mailbox. It also has the best UX: one button, one email, done, like Figma and Atlassian ([Figma Help](https://help.figma.com/hc/en-us/articles/360039820114)). The cost is one departure from ADR 0004: there is a second write path into `user_identity` besides the link endpoint, so the ADR must be amended. One large unknown remains: no document says whether Pre User Registration runs when a user is created through the Management API. Test this on a dev tenant first. The option the earlier note chose (a dedicated link connection) has a UX flaw that note did not consider: a password created on that connection cannot sign in through the main app's normal login page.

## Five workable options and four ruled out

The workable options, ordered by how much changes in Auth0:

1. **Dedicated connection for linking** (option D in `docs/research/auth0-pre-registration-link-flag.md`). The Action checks for a duplicate email only when `event.connection.name` is the main connection.
2. **Backend-signed token carried into the Action.** The token travels in an `ext-` parameter, then into a `ulp-` field through a partial. Variant: carry it in `event.transaction`.
3. **The Action asks the backend.** The backend opens a short server-side "allow window" for the email of the User who just clicked "Add a password".
4. **The backend creates the password login through the Management API.** The User sets the password through a reset email. The public sign-up form takes no part.
5. **Drop the refusal at sign-up.** Refuse only at first login with `409 account_link_required`, which already exists.

The ruled-out options:

- A plain flag on `/authorize`: Pre User Registration cannot read the query string ([Auth0 Support](https://support.auth0.com/center/s/article/Accessing-Querystring-Parameters-in-a-Pre-User-Registration-Action)).
- Gating on `event.client.client_id`: the caller chooses `client_id` on `/dbconnections/signup` ([Signup reference](https://auth0.com/docs/api/authentication/signup/create-a-new-user)).
- Auth0 native account linking: it changes the `sub` to the primary's `user_id` and removes the secondary from the user list ([Auth0 linking](https://auth0.com/docs/manage-users/user-accounts/user-account-linking)).
- Forms inside Pre User Registration: `api.prompt.render` exists only in post-login and post-challenge ([Auth0 Forms](https://auth0.com/docs/customize/forms/render)).

Passwordless OTP is also out of scope. It is not a password. Magic links only work on Classic Login. And the Action still runs for passwordless sign-up, so it meets the same problem ([Auth0 Passwordless](https://auth0.com/docs/authenticate/passwordless)).

## Details of each option

### Option 1: dedicated connection for linking

**How it works.** Create a second DB connection, for example `Username-Password-Link`, and enable it only for one link application. The "Add a password" button opens Universal Login with `connection=<link>` and `screen_hint=signup`. The Action skips every connection that is not the main one. On the main connection, the Action calls `GET /api/v2/users-by-email` and refuses on a match. The field `event.connection.name` is in the docs ([Event object](https://auth0.com/docs/customize/actions/explore-triggers/signup-and-login-triggers/pre-user-registration-trigger/pre-user-registration-event-object)). Auth0 support also calls splitting connections the most robust way to control sign-up per application ([Auth0 Support](https://support.auth0.com/center/s/article/disable-sign-ups-for-a-specific-application)).

**What it needs.** One connection and one new SPA application. An M2M application with `read:users`, with its credential kept in `event.secrets`. The backend must accept the link application's `aud` for the second login, because ADR 0004 currently accepts only the FE client id.

**Security.** The caller cannot send any value that skips the check on the main connection. The weak point: no document says `/dbconnections/signup` rejects a connection that is not enabled for the named client ([Auth0 Support](https://support.auth0.com/center/s/article/auth0-error-the-connection-is-not-enabled)). Without that check, anyone can create a user with any email on the link connection. That user cannot link, because the backend still demands a session, a nonce and `auth_time`. The result is only a denial of service on the link path for that email. Also, `users-by-email` searches the Auth0 user store, not `user_identity`. It over-counts: an Auth0 user the backend never mapped will also block sign-up.

**UX.** This is the main flaw. Universal Login uses only one DB connection per transaction. That is the first enabled connection, or the one named in the `connection` parameter ([Auth0 Support](https://support.auth0.com/center/s/article/Enabling-Multiple-Database-Connections-for-a-Single-Application)). The password lives on the link connection, which is enabled only for the link application. So the main app's login page answers "Wrong email or password". The "Forgot password" button also targets the wrong connection. I infer this from the support article; the earlier note did not consider it. To use the password, the FE would need a separate login path, so this option defeats the goal of "adding a way to sign in".

**Open questions.** Does Auth0 enforce connections per application? What are the field names in `identities`? How does the main login page behave for a user on the link connection?

### Option 2: backend-signed token carried into the Action

**How it works.** A signed-in User clicks "Add a password". The backend signs a short-lived token containing the lowercased email, `exp` and `jti`. The FE sends it as `ext-link_token` on `/authorize`. A partial on the `signup` (or `signup-id`) prompt copies the value into an input named `ulp-link_token`, hidden with CSS, because inputs with `type="hidden"` are stripped. The Action reads `event.request.body['ulp-link_token']`, checks the signature with the secret, checks `exp`, and compares the email in the token with `event.user.email`. Auth0 support describes this whole carrying path ([Auth0 Support](https://support.auth0.com/center/s/article/passing-custom-parameters-to-pre-user-registration-actions)). Variant 2b carries the token in `correlation_id` so it arrives in `event.transaction`. That field is in the list, but nobody has confirmed it is filled in on a New Universal Login sign-up ([Event object](https://auth0.com/docs/customize/actions/explore-triggers/signup-and-login-triggers/pre-user-registration-trigger/pre-user-registration-event-object)).

**What it needs.** A custom domain, Universal Login for all prompts, a Custom Page Template and a partial ([Customize prompts](https://auth0.com/docs/customize/login-pages/universal-login/customize-signup-and-login-prompts)). A secret in the Action (value up to 4096 characters) and a JWT library from npm ([Actions limitations](https://auth0.com/docs/customize/actions/limitations)). I did not check whether the tenant's plan includes a custom domain.

**Security.** Auth0 says this value is easy for users to edit and must be checked with a signature ([Auth0 Support](https://support.auth0.com/center/s/article/passing-custom-parameters-to-pre-user-registration-actions)). The token is bound to the email and short-lived. Someone who obtains the token can only create a password login for that one email, and still cannot link. A direct call to `/dbconnections/signup` carries no token, so the Action refuses as usual (fail closed). Do not reuse the ADR 0004 nonce as the token: the nonce is spent at the link step, and putting it in the URL increases exposure. The token leaks no email, because the backend signs only for the User's own email.

**UX.** The User sees the standard sign-up page. The password lives on the main connection, so normal login works. But the User still has to verify the email and then link.

**Open questions.** Some people report a partial that does not render even with a custom domain and template ([Auth0 Community](https://community.auth0.com/t/custom-partial-is-not-displayed/196758)). It is also unclear whether `correlation_id` can be set from the SDK.

### Option 3: the Action asks the backend

**How it works.** A signed-in User clicks "Add a password". The backend writes a short pending record, for example 10 minutes, for a verified email that User already has. The backend does not accept an email the user typed. The FE opens the sign-up page on the main connection. The Action calls an internal backend endpoint, authenticated with a shared secret. The backend answers only allow or deny: deny when the email belongs to a Vocab User and no unexpired pending record exists. This option needs no data carried through the login page, so it needs no custom domain. This is a design I inferred from documented capabilities, not a pattern Auth0 publishes.

**What it needs.** Outbound HTTP from the Action. Auth0's own example uses a 2-second timeout and `api.validation.error` on failure ([Pre User Registration trigger](https://auth0.com/docs/customize/actions/explore-triggers/signup-and-login-triggers/pre-user-registration-trigger)). The whole trigger must finish within 20 seconds, and outbound calls come from Auth0's published IPs ([Actions limitations](https://auth0.com/docs/customize/actions/limitations)). It also needs an internal endpoint, a pending table, and possibly an IP allow-list.

**Security.** The backend checks Vocab data, so the over-counting problem of `users-by-email` disappears. The endpoint returns only yes or no to the Action. It does not choose which User to link, so the rule "the backend never picks a User by email" still holds. But this endpoint must be internal; if it were public it would become an email-probing tool. Remaining risk: inside the window, someone who knows the timing can register that email first. They would only have an unverified user that cannot link. The victim would meet `user_exists` and recover with a password reset. Auth0 does not say what the Action does on an uncaught exception or a timeout, so every error path must call `api.access.deny` explicitly. Consequence: when the backend is down, every password sign-up is blocked.

**UX.** Same as option 2.

**Open questions.** The platform's behaviour when the Action times out. The real latency from Auth0 to the backend.

### Option 4: the backend creates the password login through the Management API

**How it works.**

1. An authenticated endpoint, for example `POST /me/sign-in-methods/password`, which may demand a recent `auth_time`.
2. The backend takes the verified email from the User's Google identity.
3. The backend calls `POST /api/v2/users` on the main connection, with a random password that is thrown away, `email_verified:false`, and a marker in `app_metadata` ([Create a user](https://auth0.com/docs/api/management/v2/users/post-users)).
4. The backend writes `user_identity` straight away from the returned `user_id`. The backend created this user, so it knows the `sub` for certain.
5. The User sets the password through a reset email. There are two ways to send it: Auth0 sends it through `/dbconnections/change_password` ([Change password](https://auth0.com/docs/api/authentication/change-password/change-password)), or the backend creates a ticket with `mark_email_as_verified`, a short `ttl_sec` and `client_id`, and sends the link itself ([Password change ticket](https://auth0.com/docs/api/management/v2/tickets/post-password-change)). This is exactly Auth0's "invite a user" pattern ([Auth0 invitations](https://auth0.com/docs/customize/email/send-email-invitations-for-application-signup)).

The repo already does this by hand in `docs/runbooks/auth0-password-user-linking.md`. `auth0-management.service.ts` can already get a client-credentials token.

**What it needs.** Scopes `create:users` and `create:user_tickets`, besides the `delete:users` it already has. A job to clean up orphan users. Possibly an exception in the Action. One community answer says the Action runs when a user is created from the Dashboard ([Auth0 Community](https://community.auth0.com/t/are-pre-user-registration-actions-run-when-new-users-are-created-through-the-auth0-ui/115480)). If that also holds for the Management API, the Action would block the backend's own call. There are two safe exceptions. The first is the mechanism from option 3: the backend writes a pending record just before it creates the user. The second is the `app_metadata` marker, if a test shows the Action can read it. The body of the public `/dbconnections/signup` has no `app_metadata`, only `user_metadata` ([Signup reference](https://auth0.com/docs/api/authentication/signup/create-a-new-user)). Never use `user_metadata` as the marker.

**Security.** Only a signed-in User can trigger it. The proof of mailbox ownership is completing the reset link. Auth0 says plainly that with a ticket the application must verify the user's identity itself ([Change users' passwords](https://auth0.com/docs/authenticate/database-connections/password-change)). So the ticket URL must never be returned to the browser. If a session is hijacked, the attacker still gets no password, because the link sits in the victim's mailbox. There is no new public endpoint. If a DB user with that email already exists (an old orphan), `POST /users` reports a conflict. In that case the backend does not link that user, and sends the User to the ADR 0004 link flow instead. That message goes only to the signed-in account owner. The architectural cost: ADR 0004 says "No Management API call is made" and links only by nonce. Option 4 adds a second write path into `user_identity`, so this path needs the same protection: throttle, logging by User id, an `auth_time` check.

**UX.** Best. The User clicks one button, receives one email, sets the password, done. There is no separate email verification step and no second link. A limit: the password uses the User's verified email. If the User wants a different email, that email belongs to no Vocab User, so #41 does not block it, and the public sign-up plus the link flow still work as they do now.

**Open questions.** Does the trigger run for `POST /api/v2/users`, and what do `event.client` and `event.user.app_metadata` contain then? Does the reset page apply the password policy and Breached Password Detection? The docs only say Breached Password Detection applies at the reset step ([Breached Password Detection](https://auth0.com/docs/secure/attack-protection/breached-password-detection)). Where does the User land after the reset on New Universal Login, since `result_url` is for Classic only? Does creating a ticket send an email by itself? Community sources disagree ([Auth0 Community](https://community.auth0.com/t/send-email-invitations-for-application-signup-no-email-sent/189320)).

### Option 5: drop the refusal at sign-up

**How it works.** No Action. `/auth/sync` returns `409 account_link_required` at first login, as the current runbook describes. The User signs in again with Google and then links. A variant uses a Post-Login Action to deny. Post-Login can read `event.request.query`, but by then the user already exists ([Post-login event](https://auth0.com/docs/customize/actions/explore-triggers/signup-and-login-triggers/login-trigger/post-login-event-object)).

**Security and UX.** There is no exception to abuse. Return the 409 only when the email is verified; otherwise anyone can probe emails by creating an unverified user. But this option does not meet the "refuse at sign-up" requirement of #41, it leaves orphan Auth0 users, and it makes the User take a detour. Keep it as a second line of defence, not as the main solution.

## Two easy-to-miss points

**First, options 1, 2 and 3 add an email verification step.** ADR 0004 requires the second login to have a verified email. A DB user created through the normal sign-up has `email_verified=false` until the User clicks the verification link; this is default behaviour I inferred and it needs a test. So after setting the password, the User must open the verification email before the link flow can run. That makes three steps. Option 4 avoids this step: a ticket with `mark_email_as_verified` sets the password and verifies the email at once.

**Second, the anti-enumeration constraint and ADR 0004 do not fully match.** ADR 0004 accepts that the refusal message at sign-up reveals that an email is registered. The task constraint says no public endpoint may reveal this. The two do not conflict if "endpoint" means a backend endpoint: the sign-up page belongs to Auth0, and Auth0 already returns `user_exists` for a duplicate within the same connection ([Signup reference](https://auth0.com/docs/api/authentication/signup/create-a-new-user)). OWASP advises a generic message at sign-up ([OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)). Consequence: the check endpoint in option 3 must be internal. Option 4 adds no new place where this leaks.

## Recommendation: option 4, with a server-side exception if needed

Choose **option 4** for the "Add a password" button. The Action keeps one rule for every public sign-up on the main connection: if the email already belongs to a Vocab User, refuse. No user has an exception. I choose this for four reasons. There is no new public surface. The password lives on the main connection, so login and "Forgot password" work normally. The mailbox is proven in the same step. And the repo already has both the Management API client and a manual runbook with the same pattern.

How to implement it depends on test 1 below. If the trigger does **not** run for `POST /api/v2/users`, no exception is needed. If the trigger **does** run, let the Action ask the backend as in option 3. The backend answers allow only when it is itself creating a user for that email within a few seconds. If instead the test shows `app_metadata` is readable in the Action and the public sign-up cannot set it, use the `app_metadata` marker. When you change the Action to ask the backend, have it check Vocab data instead of `users-by-email`, which removes the over-counting problem.

If option 4 fails a test (for example the reset page does not apply the password policy, or there is no safe exception), use **option 3**. It keeps ADR 0004 unchanged and needs no custom domain. Use option 2 only when a custom domain already exists and a tighter bound than a time window is needed. Do not choose option 1 unless a test shows the main app can sign in a user who lives on the link connection. Keep option 5 (`409 account_link_required` only when the email is verified) as a second line of defence. Option 4 needs an amendment to ADR 0004 that states the second write path into `user_identity` and why it needs no nonce.

## Tests on a dev tenant

1. Write an Action that logs `JSON.stringify(event)` for Pre User Registration, then run it three times: sign-up on the hosted page, a direct `POST /dbconnections/signup` with a different `client_id`, and `POST /api/v2/users`. Record whether the trigger runs and the values of `request.body`, `transaction`, `client` and `user.app_metadata`.
2. Send `app_metadata` in the body of the public `/dbconnections/signup`. Does Auth0 ignore it or return an error, and does the Action see it?
3. Create a ticket with `mark_email_as_verified` and a short `ttl_sec`. Check: does creating the ticket send an email itself; does the reset page on New Universal Login apply the password policy and Breached Password Detection; where does the User land after the reset; does `email_verified` become true?
4. After the reset, sign in through the normal login page on the main connection. `/auth/sync` must return the same existing User, with no `account_link_required`.
5. Run `POST /api/v2/users` when a DB user with the same email already exists. Record the error code so the backend can send the User to the link flow.
6. Make the Action throw an uncaught exception, and make it run past its deadline. Record whether the sign-up is blocked or lets through.
7. Password sign-up on the hosted page: what is `email_verified` at first, and does the link endpoint refuse until the User verifies? This applies to options 1–3.
8. Only when considering option 1: call `/dbconnections/signup` directly with the link connection and the main app's `client_id`. Then sign in to the main app with a user that lives on the link connection.
9. Only when considering option 2: does the tenant have a custom domain; does the partial render; does the `ulp-` field reach `event.request.body`; can the SDK set `correlation_id`?
10. If `users-by-email` is still used: the field names in `identities`, and the `X-RateLimit-*` headers to learn which rate-limit bucket applies.

## Conclusion

The original question was "how do we open an exception in the sign-up form". The research shows a better question is "do we need the sign-up form for this case at all". The exception options (1, 2, 3) all have to trust a signal that travels through the browser or a time window, and all add an email verification step. Option 4 removes the public form from this flow entirely, so the Action can keep one simple rule with no exceptions. What remains depends on one thing no document answers: does Pre User Registration run for the Management API? That is the first test to run.
