# Edit the success screen, not the email

Put the return-to-app line on Auth0's reset-password success screen, not in the Change Password email. The email is sent when a user asks to reset, before any new password exists, so it can only set an expectation; it cannot confirm that the reset is done. The success screen is the only post-reset surface in Auth0's default set, and its title, body and button text are editable as custom text in the Dashboard, with no Enterprise plan and no Redirect To change. The key names (`eventTitle`, `description`, `buttonText`) and their defaults are now confirmed in Auth0's primary text-elements article, which corrects the earlier community-only status. The default button reads "Back to" plus the app name, but the primary docs do not say where it goes; community reports say it follows the Application Login URI, so that destination must be tested on a live tenant before the wording promises a return. Redirect To is not Enterprise-only: it is blocked for non-enterprise tenants created on or after May 5, 2026, and the tenant's creation date decides it. None of the product help pages fetched for the seven products quotes a return-to-app success line; the closest is sign-in-again guidance from Google and Notion.

## The reset email fires before the password changes

Auth0's two Change Password templates are triggered by a user's request to change a password, and the link version contains only **a link to the reset page** ([Auth0 email template descriptions](https://auth0.com/docs/customize/email/email-templates/email-template-descriptions)). The code version adds a code to enter on that page. At send time the new password does not exist, so the email cannot report that the reset is complete. Its body can say "after you set your new password, return to Vocab and sign in," which helps a user who reads the email before resetting, but it cannot be the moment the user needs. Auth0's template descriptions list **no post-reset notification email**; the closest is a breach alert, which fires on a login with a leaked password, not on a reset ([Auth0 email template descriptions](https://auth0.com/docs/customize/email/email-templates/email-template-descriptions)). Editing the email alone therefore cannot place "return to Vocab and sign in" at the right moment. The earlier research note recommended an email-body line that says the password is already updated and tells the user to return to the app; that line is only true on the success screen and must not be used in the Change Password email.

## The success screen holds the only post-reset copy

Auth0's text-elements article confirms the `reset-password` prompt and its `reset-password-success` screen, with three editable keys: `eventTitle` for the heading, `description` for the body and `buttonText` for the button. Its defaults are a heading that says the password was changed, a one-sentence body confirming the change, and a button labelled "Back to" followed by the client name through the `${clientName}` placeholder ([Auth0 text elements](https://auth0.com/docs/customize/login-pages/universal-login/customize-text-elements.md)). The Dashboard path is Branding, Universal Login, Advanced Options, Custom Text; select `reset-password` and `reset-password-success`, edit, check the live preview and save. The Management API equivalent is `PUT /api/v2/prompts/{prompt}/custom-text/{language}`, which needs the `update:prompts` scope and **overwrites all existing text for that prompt and language**, so every screen key must go in one call ([Auth0 Management API: set custom text](https://auth0.com/docs/api/management/v2/prompts/put-custom-text-by-language)). That endpoint page does not describe the body shape. The screen-then-key nesting comes from a Pulumi example for the login prompt ([Pulumi auth0 prompt custom text](https://www.pulumi.com/registry/packages/auth0/api-docs/promptcustomtext/)) and a community reply.

The button destination is the open question. The Application Settings article describes the Application Login URI as the route that forwards users to the tenant's `/authorize` endpoint, and it does not connect that field to the success-screen button ([Auth0 application settings](https://auth0.com/docs/get-started/applications/application-settings)). An August 2022 community answer says the button links to the Application Login URI ([community thread](https://community.auth0.com/t/customize-message-for-navigation-button-on-password-reset-page/88688)). A search summary of another community thread reports a fallback to the tenant Login URI, but that thread could not be retrieved, so the fallback is unverified. A December 2024 thread reports a missing button on a Management API reset, traced to a wrong client_id; that is also community-only. Until the destination is tested, a button labelled "Return to Vocab" may land somewhere other than the sign-in page.

## Redirect To is date-gated, and it is not the fix

The brief treated Redirect To as Enterprise-only. The docs are narrower: **tenants created on or after May 5, 2026 with a non-enterprise subscription cannot customize Redirect To; tenants created before that date are exempt** ([Auth0 customize email templates](https://auth0.com/docs/customize/email/email-templates/customize-email-templates)). The Change Password (link) template lists the field, so the restriction applies there. The same page says Universal Login ignores Redirect To in the Password Reset template, which is a different template, and it does not say what the Change Password Redirect To does after a successful reset. The docs tie the field to completing an action at an included link, not to the reset result, so it is not a success message and is not a fix. The tenant's creation date is shown in the Teams Dashboard, where each tenant lists a Creation date ([Auth0 tenant management](https://auth0.com/docs/get-started/auth0-teams/tenant-management)). Check that date only to learn whether the restriction would ever apply; the recommendation below does not depend on it.

## Seven major products stop at sign-in-again help text

The earlier pass fetched help pages for Google, Microsoft, Slack, Notion, GitHub, Stripe and Dropbox. **None of the fetched pages quotes an on-screen success message**, so exact success wording is unverified for all seven, and Microsoft's official consumer page was not retrieved. Where a next step appears, it sits in help text: Google's account help says that after a change you are signed out of other devices and may need to sign in again ([Google Account Help](https://support.google.com/accounts/answer/41078)), and Notion's final step says to log in again ([Notion Help](https://www.notion.com/help/cant-log-in)). Slack's reset article and Stripe's fetched article contain no post-reset copy. Dropbox's article says a password cannot be reset in the mobile app and directs users to a browser ([Dropbox Help Center](https://help.dropbox.com/accounts-billing/settings-sign-in/password-reset)). GitHub's only post-reset step is an optional sign-out of GitHub Mobile ([GitHub Docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/updating-your-github-access-credentials)). No fetched source describes a return-to-app link or an automatic redirect for any product, so "return to the app" is an Auth0 default to design around, not a pattern these sources establish as industry norm. NN/g's error-message guidance supports the principle that naming a problem is not enough and users need a next step ([NN/g error-message guidelines](https://www.nngroup.com/articles/error-message-guidelines/)), but it covers errors, not success messages. GOV.UK and Apple HIG guidance were not retrieved in usable form, so they are not used here.

The first surface to change is the Universal Login reset-password success screen, through the Dashboard Custom Text tab, for the New Universal Login prompt. It is the only surface that appears after the reset, its key names and defaults are now verified in primary docs, and it needs neither an SMTP change nor a Redirect To change. Edit `description` and `buttonText` first, use the live preview, and test the button destination on a non-production tenant before anything ships. Only then consider the Change Password email, which is an expectation line rather than the fix. Editing that email requires an external SMTP provider, because the built-in provider does not allow template customization; that point comes from the earlier pass and was not re-checked here.

## Conclusion

The return-to-app problem is a two-step problem, and the two steps sit on different surfaces. The email sets the plan by telling the user what to do after resetting; the success screen closes the loop after the reset. Auth0's only verified post-reset surface is the success screen, and the only verified return path is its button, whose correctness depends on an Application Login URI setting that the wording cannot change. That makes a return-to-app line only as reliable as the destination behind it, so the destination test should come before the copy edit goes live. Redirect To, which the brief framed as the Enterprise blocker, is a date-gated restriction and a poor fit for a success message in any case. The major products in this sample show no return-to-app success line in their help text, which stops at sign-in-again; that suggests the Vocab wording should name the destination and the password to use, as the four lines above do.
