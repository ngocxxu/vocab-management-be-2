# Auth0 account linking in practice (email+password, then Google, same email)

Research date: 2026-10-17. Primary sources only (Auth0 docs, OpenID Connect Core spec, Supabase docs). Anything not confirmed on a primary page is marked **unconfirmed**. Pages were read through a fetch tool that summarises content, so quotes are short and should be re-checked on the page before being copied into an ADR.

Question: when a user signs up with email+password and later signs in with Google using the same email, what do production apps do on Auth0, and should this repo keep "never link automatically, never by email" (ADR 0003, 409 `account_link_required`)?

## 1. Auth0 default behavior

- Auth0 does not merge by email. "Auth0 treats all identities as separate by default." A user who signs in with the Auth0 database connection and later with Google can appear as two different users. Source: https://auth0.com/docs/manage-users/user-accounts/user-account-linking
- Linking is an explicit operation: a primary and a secondary account are merged. The result keeps the primary `user_id`; the secondary moves into the primary's `identities` array and disappears from the user list. Metadata is not merged automatically, and the secondary's metadata is discarded unless the caller merges it first. Deleting the primary also deletes the linked secondary. Sources: https://auth0.com/docs/manage-users/user-accounts/user-account-linking and https://auth0.com/docs/manage-users/user-accounts/user-account-linking/user-initiated-account-linking-client-side-implementation
- Consequence for this repo: with no linking, the second login arrives at the backend as a different `(issuer, sub)` pair carrying the same email. That is exactly the case ADR 0003 turns into 409. This matches the OIDC rule that `iss`+`sub` is the stable identifier and that `email` "MUST NOT be used as unique identifiers" (OIDC Core section 5.7: https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability).
- Note: with Auth0 linked identities, the ID token `sub` is the primary user's id even if the user logs in with the secondary. Auth0's Action docs say it does not automatically switch to the primary user after linking; the Action must do it. Source: https://auth0.com/docs/manage-users/user-accounts/user-account-linking/link-user-accounts (the Action sample uses a "set primary user" step; the exact API name, `api.authentication.setPrimaryUser`, comes from an Auth0 Community thread, which is not a primary source: unconfirmed).

## 2. Documented options and Auth0's stated risks

Auth0 documents three mechanisms (https://auth0.com/docs/manage-users/user-accounts/user-account-linking/link-user-accounts): an Action plus an external linking app, the Management API, and Auth0.js. Mapped to the three scenarios you asked about:

| Option                                           | How it works per Auth0 docs                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Auth0's stance                                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Automatic linking in an Action by verified email | An Action finds candidate users by email and calls the link endpoint. Auth0's own sample only processes users whose email is verified and only considers candidates with verified email.                                                                                                                                                                                                                                                                                                                           | Discouraged. See section 3. Auth0 states: "You should not automatically link accounts based on the user's emails" and recommends prompting re-authentication. Source: https://auth0.com/docs/manage-users/user-accounts/user-profiles/verified-email-usage                                                                                                                                                   |
| Suggested / server-side linking (semi-automatic) | App authenticates user, looks up accounts with the same verified email via Management API, prompts the user to choose, makes the user authenticate to the target account, checks the target `sub` matches, merges metadata, then links. Should ask the user's permission first. Source: https://auth0.com/docs/manage-users/user-accounts/user-account-linking/suggested-account-linking-server-side-implementation                                                                                                | This is Auth0's recommended pattern ("linking only after the user proves access to both"). Also packaged as the Account Link Extension: https://auth0.com/docs/customize/extensions/account-link-extension                                                                                                                                                                                                   |
| User-initiated linking                           | Signed-in user clicks "Link account" in the app, authenticates to the second account via Universal Login, the app calls `POST /api/v2/users/{primary_id}/identities` with the secondary's ID token as `link_with`. Needs an access token with `update:current_user_identities`; sample code rejects an unverified secondary email. Sources: https://auth0.com/docs/manage-users/user-accounts/user-account-linking/user-initiated-account-linking-client-side-implementation and the link-user-accounts page above | Fine; both accounts are authenticated by the same human in one session.                                                                                                                                                                                                                                                                                                                                      |
| Manual / admin linking                           | Server-side call to the same endpoint with an access token carrying `update:users` (can modify any user, so server-side only). Source: https://auth0.com/docs/manage-users/user-accounts/user-account-linking/link-user-accounts                                                                                                                                                                                                                                                                                   | Auth0 says every manual link should prompt the user to enter credentials, and both accounts should be authenticated before linking. Source: https://auth0.com/docs/manage-users/user-accounts/user-account-linking. An admin link where nobody re-authenticates either account sits outside that guidance: unconfirmed whether Auth0 considers an admin-vetted link acceptable (the docs do not discuss it). |

Stated risks:

- "Insecurely linking accounts can allow malicious actors to access legitimate user accounts." Source: https://auth0.com/docs/manage-users/user-accounts/user-account-linking
- Attack scenario on the verified-email page: an attacker creates a database user with the victim's email, links it to their own account, then phishes the victim into resetting the password and logging in; "The user enters their password and logs into the attacker's account" and the attacker gets whatever data the victim enters. Source: https://auth0.com/docs/manage-users/user-accounts/user-profiles/verified-email-usage
- Operational gotchas: if linking fails in the sample, it only logs and continues; linking during an active login can break the `/continue` redirect; the primary choice decides which attributes survive. Sources: server-side page and link-user-accounts page above.

## 3. Conditions Auth0 recommends before linking

1. Both accounts authenticated by the same person. Auth0: "The only way to achieve that is to have users authenticate with both accounts before linking them." Source: https://auth0.com/docs/manage-users/user-accounts/user-profiles/verified-email-usage. The Account Link Extension repeats it: it "does not automatically link users with the same email, even if emails are verified", because "verified emails are not enough evidence to prove that the user can currently authenticate to both accounts." Source: https://auth0.com/docs/customize/extensions/account-link-extension
2. `email_verified` is a mitigation, not a substitute. Auth0 lists why: verification happens once at one moment (addresses get reassigned, e.g. ex-employee mailboxes), and for federated providers Auth0 copies the provider's claim, so correctness depends on the provider, which "can make mistakes". Source: https://auth0.com/docs/manage-users/user-accounts/user-profiles/verified-email-usage
3. Check `email_verified` on every candidate before linking (Auth0's sample code does so for both primary candidate and secondary). Sources: link-user-accounts and user-initiated pages above.
4. Ask the user's consent in the flow. Source: server-side page above.
5. Do not use email domain as an authorization signal. Source: verified-email-usage page.
6. Spec backdrop: `email_verified` true means the OP "took affirmative steps" to ensure the address "was controlled by the End-User at the time the verification was performed" (OIDC Core section 5.1: https://openid.net/specs/openid-connect-core-1_0.html#StandardClaims). That is a point-in-time claim by the provider, matching Auth0's caveat.

Not found on a primary page (unconfirmed): whether Auth0's Google social connection always sets `email_verified: true`; a specific Auth0 changelog or blog entry about changing linking defaults; any published Auth0 statistics on what production customers actually do. Auth0 Community posts describing "link in a post-login Action when both identities share a verified email and come from trusted IdPs" exist but are community guidance, not Auth0 policy, and were excluded as non-primary.

What "production apps do in practice" therefore comes only from what Auth0 documents and tools (extension, sample Actions); Auth0 publishes no usage survey (unconfirmed).

## 4. Comparison with Supabase

- Supabase defaults the other way: "Supabase Auth automatically links identities with the same email address to a single user." It requires emails to be unique. Source: https://supabase.com/docs/guides/auth/auth-identity-linking
- Its safeguard is verification, not re-authentication: auto-linking an identity to a user with an unverified email "would be insecure" (pre-account takeover), so it avoids that case and, when a new identity links to a user, removes other unconfirmed identities on that user. Source: same page.
- Manual linking (`linkIdentity()`, beta, off by default) is for a signed-in user adding an identity, including one with a different email. SAML SSO users are excluded from both automatic and manual linking. Source: same page.
- Supabase support has said the `email_verified` value depends on the OAuth provider and cannot be overridden (a GitHub discussion, so not first-party documentation; treat as unconfirmed): https://github.com/orgs/supabase/discussions/20191
- Net difference: Supabase relies on provider-verified email as the trust anchor and links silently; Auth0 documents the same threat model but concludes silent linking is not enough and asks for proof of both credentials.

## 5. Recommendation for a small app (about 8 users, backend already requires `email_verified`)

| Option                                                                | Fits when                             | Risk                                                                                                                                                   | Cost here                                                                                                                                                      | Verdict                                    |
| --------------------------------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| A. Keep ADR 0003 (409 + admin link)                                   | Few users, rare collisions            | Lowest. No email-based trust. Admin link has no user re-authentication, so the admin must verify out of band (unconfirmed whether Auth0 blesses this). | Zero code; an admin step per collision (~8 users)                                                                                                              | Recommended default                        |
| B. Silent auto-link in a post-login Action on verified email          | Large user base, low-sensitivity data | Contradicts Auth0's explicit guidance; depends on every upstream IdP's `email_verified` being honest and current                                       | Medium, plus loses the audit trail that the Identity table gives                                                                                               | Not recommended                            |
| C. User-initiated linking (signed-in user clicks "link Google")       | Users want self-service               | Low: the user has authenticated to both in one session                                                                                                 | New endpoint/UI, backend must accept the linked identity and keep Identity rows `(issuer, sub)` consistent with Auth0's primary-`sub` behaviour                | Good upgrade if admin links become a chore |
| D. Suggested linking (Account Link Extension or the server-side flow) | Colliding users are common            | Low (re-auth to both accounts)                                                                                                                         | Extension setup, Auth0 plan limits may apply (plan availability is stated as variable: https://auth0.com/docs/manage-users/user-accounts/user-account-linking) | Overkill at 8 users                        |

Reasoning for the table, checked against this repo's design: because the backend keys `Identity` on `(issuer, sub)` and does not treat email as an identifier, it already follows the OIDC rule (section 5.7). Requiring `email_verified` blocks the classic "unverified email" attack, but Auth0 says that alone does not prove current control, and a pre-registered password account with the victim's email is exactly its attack scenario. At 8 users, the cost of manual linking is negligible and the failure mode of silent linking is full account takeover, so keep A and move to C only if collisions become frequent. If you adopt C or D, link on the Auth0 side and make sure the backend maps the post-link `sub` (primary id) to the existing local User, or the linked login will look like a new identity.
